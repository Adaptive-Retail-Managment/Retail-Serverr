# Requirements traceability matrix — Step 3 database design

**Status:** Reconciled against the authoritative
[Master Project Requirements & Decision Document](MASTER_PROJECT_REQUIREMENTS_AND_DECISION_DOCUMENT.md)
(MRDD v1.0, baseline 18 November 2026), incorporated 22 November 2026.

**Authority rules applied**

- MRDD sections cited as `§n` / `§n.m`; numbered decisions as `D-n` (MRDD §24 register,
  decisions 1–190); grouped finalizations as `GF-*` (MRDD §25).
- **Later owner-confirmed decisions outside the MRDD** are labelled explicitly: **U-1 Option A**
  (same-branch PO/receipt) and **D-025** (strict offline-sale rejection). These are architecture /
  owner decisions recorded in `ARCHITECTURE_DECISION_RECORDS.md`, not MRDD baseline text.
- **Technical decisions** (Prisma, composite keys, companion SQL, module ownership) are design
  choices, not requirements; they are labelled **TECH**.
- Enforcement layers: **DB** = schema/constraint, **SVC** = service/application (Step 4+),
  **AUTH** = authorization layer, **UI** = interface, **OPS** = operational process.

## Genuine gaps

- **None blocking.** All catalog requirement areas map to real MRDD sections. Items marked
  "SVC"/"Partially represented" are intentionally application-enforced per the documented
  enforcement-layer model — not schema defects. §27 items (state machines, RPO/RTO, customer
  uniqueness, landed-cost allocation, currency rules, retention) remain open technical decisions
  by design and are not requirements gaps.
